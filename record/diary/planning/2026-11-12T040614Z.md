# planning, 2026-11-12 04:06Z: the first Road Bible

This PR's own entry. The PR adds `record/road-bible.md` and this entry, and changes nothing else.

**What it is written from.** rulings.md R5, R6 and R8 (how the rules apply to a mod that already ships),
R9 to R15 (the owner's earlier rulings, carried in), and R22 to R24 (the owner's rulings of 2026-11-12 on
the kill streak, the Hunter and the prototype). I also read the code and `README.md`, `CLAUDE.md` and
`docs/moddb.md` on main at `60946d8`, and the old design document, the creature bible, which is outside
the repo.

**Two marks, so that a reader can check each sentence.** (R9) and the like name the ruling a sentence
rests on. (1.1.1) is on a sentence that no ruling backs and that describes the mod as it was designed and
ships: one victim at a time, the five STAGES and the cap at STAGE 3 in company, the gaze, the tells, the
cap on one blow, the three ways to banish, the player's own comforts. They come from the creature bible
and I checked the ones that are numbers against the code (`ladder.groupStageCap` 3, `forms.maxHitFraction`
0.4, `return.afterSeasons` 2). The creature bible is not in the record, so the Road Bible states these
itself and the owner's merge is what makes them stand. Why not leave them out: every builder and the
review thread need the whole creature in one place, and a book that named only what was ruled would have
no gaze and no STAGES in it.

**What I added to the owner's words about the Super Predators.** R9 says what the Goblin and the Hunter
are. It does not say which of the walker's rules they keep. The Road Bible says they keep four that the
owner ruled for the mod as a whole: one real creature (R10), ended by silver and fire (R10), never
insurmountable (R11), and harm that is counted, capped, mindful of land claims and switchable (R11, R12).
It says they depart from two, as R9's own words require: the Goblin's harm lasts, and the Hunter is
stronger and passes plain walls (R23, "tentatively"). Everything else about them is left to their briefs.
This is the planning thread's development of R9, not a ruling, and the PR's description points the owner
to it.

**Decisions.**

1. *Four builder role names, one to a part of the code:* `director`, `creature`, `harass`, `commands`.
   Not one thread per feature, and no thread of its own for each Super Predator. Why: a thread has one
   unmerged feature at a time (rule 3), and the features of one part of the code come one after another
   anyway; and every need that crosses two threads costs an entry in rulings.md before either acts
   (rule 1). The fight (feature 9) reaches into both the stalker's and the forms' folders, so one thread
   owns both. The Goblin grows out of the harassment kit and the Hunter out of the stalker's code, so
   they go to those threads. In step 3 each of three threads has one feature. Why not more threads: more
   would start sooner, and the owner's order is the immediate before the distant (R24).
2. *The six shipped features are listed under no step.* They are complete, and the PRs that completed
   them were merged before these rules. A step's gate counts "the PR that completes" each of its features
   (rule 7); under a step they would either pass that test at once and mean nothing, or fail the tests
   that ask for a diary entry. Why not a step of their own for writing the as-is briefs: R6 asks for such
   a brief before a thread first touches its feature, not for all six before anything else, and a
   stock-take step would hold the faster return behind briefs for features this road does not touch.
3. *Each piece of new work is a new feature with its own number and brief, even where it lives in a
   shipped feature's folders* (7 to 10). Why: only a feature has a PR that completes it, so only a
   feature can be counted by a step's gate. Why not a change to the shipped feature's brief followed by a
   patch: rule 4 allows that, but no gate would then know whether the faster return was done. The cost is
   two briefs that touch: the book says the later feature's brief PR changes the earlier brief too, so
   that every settled brief stays true as written.
4. *Feature 7, settings that follow the version, is in step 1.* No ruling asks for it. Version 1.1.1
   keeps every value already saved in a world's settings file and adds only settings the file lacks
   (`WalkersConfigSystem.cs`, WriteBackIfClean), so a changed default never reaches a saved world, the
   owner's own included. Without it the faster return would show only on new worlds.
5. *The workshop is feature 9's brief.* R9 asks for a workshop on stats and intelligence. Under these
   rules a design is settled through a brief's questions, asked together, and in play. Why not a
   workshop thread of its own, as the old project had: it would settle a design outside the one place
   rule 2 gives for it.
6. *Step 3 waits whole,* a brief or an experiment included, until step 2 has passed its gate. Reasons in
   `2026-11-12T040029Z.md` (branch `claude/planning-rulings`).
7. *The prototype's terms* follow R24: the faster return and a retuned fight, reached by admin commands
   in ten minutes, no Super Predator. Added by me: everything it adds is off until an admin switches it
   on, so that main stays what version 1.1.1 is for anyone who builds it; what it changes goes in the
   folders of the features that will take it over (THE CAST gives those parts to their owners once it
   merges); and its own folder holds only the switch and the commands and is removed before step 1 is
   reported done, so that no builder's change can break code that only the proto thread may repair.
8. *The shared list.* `proto` owns the checks, the build, `CLAUDE.md`, `README.md`, the changelog, the
   page's text and the mod's card; `commands` owns the code every feature starts from. Why `proto`: SETUP
   already gives it the checks workflow, R8 needs one thread to bring `CLAUDE.md` and `README.md` in line,
   and a release PR touches all of these at once. `LICENSE` has no thread. A path that falls under no row
   is added to the list before anyone creates it.
9. *A release is the owner's call, after any step.* The road does not say that all three steps make one
   version.

**The check on ownership.** A script took the tables of parts 3 and 4 as patterns and ran them over
every file on main outside `record/`: 201 files, each under exactly one row, none under two, and no
pattern that matches nothing. The script is `road-bible-owners-check.py` in the project's shared files
folder under `planning/`.
