**Decisions, and why.**

1. **The paragraph on the section `proto`.** The "Done" line has step 1 hold "on an installation whose
   settings file an older version of the mod wrote as on a fresh one", and the row of feature 7 speaks
   of the same files. The prototype's build adds a section `proto` to the settings file of an
   installation it loads on. When the proto thread removes its folder, the file that defines the
   section goes with it (part 4), and the section is left in the settings file as a setting the mod
   does not know. The review thread tried it (G40): the server logged "Unknown setting, ignored:
   proto", and a setting that the file lacked "was not added to the file". So a builder could ask
   whether step 1 has to hold on such a file, and whether feature 7 has to deal with it. The book
   now says: no.
   - Why not have feature 7 deal with it. G40 named the ways out and left the choice to the proto
     thread, and the proto thread chose: the owner deletes the section by hand, and the removal PR
     and the word that goes with step 1's zip say so (its map, step 8; G49 has the flaw corrected).
     Only an installation that has loaded the prototype holds the section, and the early zip goes to
     the owner alone (rule 3). To make feature 7 clean up after the prototype would add to what
     feature 7 is, for one file that a hand's edit puts right. That would be a change to a feature,
     and more than item 2 set out to do.
   - Why the row of feature 7 is named, where my map had only "the files that line speaks of". The
     row speaks of the same files in nearly the same words: "An installation whose settings file was
     written by an older version of the mod". A sentence about the "Done" line alone would leave open
     whether the row still covers such a file, and that would be two readings (rule 1). So the
     paragraph says what such a file does not count as, in both places.
   - Why the reason stands in the book. Without it "does not count" is a bare exception. With it the
     brief of feature 7 has what the loader of version 1.1.1 does with such a file. The sentence
     carries the mark (1.1.1), and I tested it against the code (below). It says only what is true of
     the file: a setting the file lacks still takes its default in the running mod, as the row of
     feature 7 says, and is only not written into the file.
   - Why "by hand", and no name. The last sentence says when such a file counts again. It gives no
     one a duty. Who tells the owner is in the proto thread's plan. Why not name the proto thread: a
     duty of the proto thread for what the prototype leaves behind would be one of the prototype's
     terms, which are part 2, and this change is to part 3 alone.
   - Why a paragraph of its own, and not one more sentence in the "Done" line. The line says what the
     owner can do when the step is done, and the owner merged it in those words. The paragraph says
     which files the line speaks of.
   - Why nothing is said of a settings file with comments, or with a setting that an admin mistyped.
     The loader of version 1.1.1 writes nothing into those either. But they are the admin's doing,
     and what feature 7 does for them is for its brief to ask. The section `proto` is the one case in
     which a build of the mod itself left the file so.
2. **Row 9: "the settings and the numbers fixed in the code alike".** G42, point 4, found that the
   numbers of the fight are not all settings, and named five that are fixed in the code. The row has
   `creature` bring "the numbers as they stand", and by G42 "that list is longer than the settings".
   Why not list them in the book: the list is the brief's to make, from the code as it stands on the
   day the brief is written, and a list in the book would be a second place to keep true. Why not
   write "the numbers of version 1.1.1" instead: part 2 already says what features 8 and 9 start
   from, and "as they stand" stays true if a patch changes a number before the brief is written.
3. **Rows 8 and 9: what the prototype tried.** Under R45 the prototype's numbers are removed with its
   folder, and since PR #105 part 2 keeps them in the record: "What the prototype tried stays in the
   record: the entry that its PR carries in the proto thread's diary holds every number that the PR
   lists (point 4)." What the owner says after playing the prototype is said of those numbers, and
   once the prototype's folder is removed the code no longer holds them. The rows now send the two
   threads there.
   - Why "for the return" and "for the fight". The proto thread's entry lists eleven numbers: two
     stand in for settings of the return, and nine for settings of the fight, two of them of the gaze.
   - Why "(part 2)" and not the name of the entry. Part 2 says which entry it is, in words that hold
     whatever its file is called. And the entry rides in PR #75, so it is not on main until the owner
     has merged the prototype.
   - Why the rows give no reason. Part 2 gives it, in the paragraph that the rows point to.
   - Where it came from. Reading PR #105, the review thread asked how the row of feature 9 is to be
     read under R45, since "nothing that the prototype tried stays in the code by itself" (G53), and
     I answered that the row would say so at the book's next change. The words of this change are
     mine. The review thread has said that its question does not keep it from certifying, and that
     its report will say where the third thing came from (G58).
