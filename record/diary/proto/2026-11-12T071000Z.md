**Decision: how the prototype's fight retune reaches the walker without anything depending on my folder.**
Part 2 says nothing outside `Walkers/Proto/` may depend on anything inside it, and that what the
prototype changes about the fight goes in the folders of features 2 and 3. Every number of the fight
that does not belong to the gaze rule is already a setting of features 2 and 3 (`forms.trueHealth`,
`forms.trueDamage`, `forms.attackCooldownMs`, `forms.retreatHealth`, `stalk.chaseSpeed`,
`stalk.stalkSpeed`, `stalk.lungeCooldownSeconds`), and the code of those features reads each value at
the moment it uses it. So the first retune needs no change in those folders: while the prototype's
switch is on, the proto system lays its own values over those settings in the server's live config, and
when the switch goes off it reloads the file, which puts every value back as the admin wrote it. The
file itself is never written with the prototype's values. Why not new code in `Walkers/Stalker/` or
`Walkers/Forms/` that reads the switch: that would make those folders depend on mine. Why not change the
defaults in those folders: then the walker would differ from 1.1.1 with the prototype off, against
part 2, point 1. If a later retune needs a knob that is not yet a setting, it goes into the feature's
folder as a new setting whose default is the shipped value, and my PR lists it.

**Decision: where the switch lives.** A section `proto` of `ModConfig/walkers.json`, in
`Walkers/Config/WalkersConfig.Proto.cs`, which part 4 names as mine, with `proto.enabled` off by default.
It is set like any other setting, and by `/walkers proto on|off`. The cost: a server that loads the
prototype gets the new section added to its settings file, as a new release adds any new setting. The
world's save is not touched while the switch is off. Why not a file of its own: the project's pattern is
one settings file, and `/walkers config` then shows and explains the prototype's numbers to the owner.
